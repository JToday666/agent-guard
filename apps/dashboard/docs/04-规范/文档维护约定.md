# 文档维护约定

本文约定 Dashboard 前端事实写在哪里，以及更新文档时必须遵守的边界。

## 1. 文档分工

### 1.1 `apps/dashboard/README.md`

维护前端应用入口信息：

- 技术栈
- 常用命令
- 目录概览
- 文档索引
- 前端与 Core API 的边界

不维护复杂页面逻辑、接口字段细节或跨端契约。

### 1.2 `apps/dashboard/docs/**`

维护前端内部事实：

- 页面、路由、布局和导航约定
- 组件、store、composable、API 门面和状态模型
- UI、可访问性、文案和文档规范
- 前端如何消费 Core API、trace、metrics、approvals

不维护 Core 规则、Adapter 行为、AttackBench ground truth 或 OpenClaw Hook 语义。

### 1.3 根目录 `docs/**` 与 `schemas/**`

维护跨端事实：

- 系统架构和阶段边界
- Core API、事件模型、字段语义和决策契约
- JSON Schema、OpenAPI 和契约测试依据
- Redteam、AttackBench、Adapter 和 OpenClaw 设计

前端文档引用这些事实时使用链接和简述，不整段复制。

## 2. 单点维护

同一个事实只能有一个主维护位置：

- `AuditEvent` 字段：根目录 `docs/02_core/interface_contract.md` 或 `schemas/**`
- Dashboard 如何展示 `AuditEvent`：`apps/dashboard/docs/**`
- 前端运行命令：`apps/dashboard/README.md`
- 页面文案、布局和 UI 约束：`apps/dashboard/docs/04-规范/**`

其他文档如需提及，使用“简述 + 链接”。

## 3. 文档深度

- README 写入口、命令、索引和边界。
- docs 写模块职责、数据流、状态流、页面结构和关键约定。
- 普通展示组件只写用途、输入输出和依赖关系。
- 复杂 store、composable、API 门面、轮询、状态机和错误恢复必须写清调用顺序。

## 4. 更新触发

出现以下变化时，必须评估是否更新前端文档：

- 新增、删除或重命名页面
- 路由、布局、导航变化
- 新增共享 UI、store、composable 或 API 门面
- Core API 消费方式、环境变量、运行时配置、鉴权状态模型变化
- loading、empty、error、forbidden、approval 等状态模型变化
- 文案、可访问性或视觉规范变化

## 5. 写作要求

- 文件名、目录名、路由名、模块名、环境变量名必须以仓库真实内容为准。
- 未来规划必须明确标注，不得写成当前事实。
- 增加链接后，定向检查相对路径是否可达。
- 优先写调用顺序和职责边界，不写无价值目录罗列。
- 文档修改必须聚焦当前任务，不顺手改无关历史内容。

## 6. 边界

- `apps/dashboard/docs/**` 是前端内部文档，可在前端任务中维护。
- 根目录 `docs/**` 只在任务明确授权且与当前任务直接相关时修改。
- `apps/guard-api/**`、`packages/**`、`redteam/**`、`schemas/**`、`policies/**` 不属于前端文档任务范围。
