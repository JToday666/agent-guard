# 1. Freeze Review Questions 逐条处置

处置分两类：

- **契约级直接关闭**（14 项）：答案已完整落入机器冻结文件 `context_taint_contract_freeze.yaml` 与既有章节，不再依赖实现细节。

## CT-Q-01

**问题**：哪些 source 能 server-side trusted？

**裁决**：仅服务端 authenticate 的 producer 可出 authoritative record；外部来源（web/email/rag/tool_result/mcp）一律 `trust=untrusted`、`fact_authority=untrusted_claim`、`initial_taints=[UNTRUSTED]`。Adapter 自报的 trusted 不构成 server-side trusted。

**依据**：`yaml:source_defaults`；09 章 D-04（Fact Authority 先于 Fact Producer）；02 章 Fact Authority Matrix。

## CT-Q-02

**问题**：trusted tool 是否与 trusted tool output 区分？

**裁决**：区分。tool 程序本身可被 authenticated（运行身份可信），但其返回内容仍是 `untrusted_claim`，`tool_result` 默认 `UNTRUSTED`。trust 升级必须经服务端验证，不得由 tool 身份自动继承给输出内容。

**依据**：`yaml:claim_rules`（trusted tool execution != trusted tool output content）；03 章；02 章 Verified Fact Producer 边界。

## CT-Q-03

**问题**：Adapter 何时只有 claim authority？

**裁决**：Adapter 恒为 claim authority（claim 提交者，不是事实签发者）。仅 risk-increasing 方向的 claim 可被保守接受；Adapter 不可自升 trust、不可去 taint、不可提交 SecurityStateDeltaV21。

**依据**：不变量 CT-F0-07；`yaml:claim_rules`；09 章禁止事项。

## CT-Q-04

**问题**：model output 如何传播 taint？

**裁决**：LLM 是不透明变换：除 deterministic evidence 外，跨 LLM 的流默认且最高为 `possible`；LLM 既不是 sanitizer 也不是 authority issuer，穿越 LLM 不得清除 taint。

**依据**：09 章 D-07；`yaml:flow_strength.llm_default`；不变量 CT-F0-02 / CT-F0-06。

## CT-Q-05

**问题**：strong transformation whitelist 是什么？

**裁决**：决策关闭，参数延后。weakest-edge 路径聚合规则与「strength 升级到 strong 必须来自具名白名单变换（deterministic evidence）」的原则冻结；白名单成员清单延后至 CT-PR-04 实施时确定并纳入 contract tests。

**依据**：08 章 CT-PR-04 范围；`yaml:flow_strength.path_aggregation`；04 章。

## CT-Q-06

**问题**：current facts 如何进 assessment？

**裁决**：仅以 `TransientSecurityFacts` 作为 pre-commit 证据参与当前事件判定；不写历史 state，不参与跨事件结论。

**依据**：不变量 CT-F0-09；01 章 TransientSecurityFacts；09 章 D-05。

## CT-Q-07

**问题**：current facts 何时进 history？

**裁决**：仅 committed authoritative record 之后，经 typed projection（delta 投影）进入历史状态；current event pre-commit 阶段禁止任何 OnlineState 变更。

**依据**：不变量 CT-F0-08；`yaml:state`（三个 false）。

## CT-Q-08

**问题**：Memory clean 的必要条件？

**裁决**：ALLOW ≠ TRUST。Memory clean 的必要条件是：来自干净来源链的 authoritative MemoryFact，或经合法 declassification（trusted_declassifier + registry 许可）。memory write 被 allow 不自动 clean。

**依据**：09 章 D-09；04 章 Memory；`yaml:declassification`。

## CT-Q-09

**问题**：PERSISTENT_UNTRUSTED 如何重启恢复？

**裁决**：双通道恢复：① sticky taint summary 受驱逐保护（`protected_labels` 永不按普通淘汰移除）；② 重启后由 committed authoritative record rebuild 恢复。flood 之后 persistent evidence 必须仍在。

**依据**：`yaml:declassification.protected_labels`；04 章 provenance sticky 纪律；07 章 Flood 测试。

## CT-Q-10

**问题**：declass proof 从哪里查？

**裁决**：committed `DeclassificationFact` + 服务端 registry 许可双查；Snapshot 阶段只做 bounded lookup，不扩张新的 OnlineState 域。registry 不可用时 fail-closed。

**依据**：09 章 D-10；CT-PR-06 范围；`yaml:declassification.protected_removal_requires_registry_permission`。

## CT-Q-11

**问题**：lookup 截断如何降 Coverage？

**裁决**：provenance lookup 超出 depth/breadth/node budget 即 `truncated=true`，coverage 降为 partial/unknown，fail-closed 处理——截断不当作 safe，不得 CLEAR_ALLOW。

**依据**：不变量 CT-F0-05；`yaml:budgets`；07 章 Lookup Truncation。

## CT-Q-12

**问题**：no grant 是 unknown 还是 unauthorized？

**裁决**：冻结为 unknown 优先：no grant 通常判 unknown，不由 Context/Taint 强制 unauthorized；执行侧的最终裁定（unauthorized vs unknown 的后果）归 Core V2.1 Fusion 的 machine matrix。

**依据**：09 章 D-12；`yaml:fusion.machine_truth`。

## CT-Q-13

**问题**：B2 是否 standalone deny？

**裁决**：否。B1-B6 全部 signal-only：只产出信号进入 Fusion，最终决定由 Fusion + Authority（Core V2.1 单 PDP）做出；任何 behavior matcher 不得 standalone deny。

**依据**：09 章 D-11；不变量 CT-F0-10；`yaml:fusion.behavior_signal_standalone_deny=false`。

## CT-Q-14

**问题**：DENY 如何证明没执行？

**裁决**：DENY 决定不自动证明未执行；`RuntimeOutcomeReceipt` 是唯一执行真值。没有 receipt 不得宣称 not_invoked；deny 自动写 not_invoked 属禁止事项。

**依据**：不变量 CT-F0-04；09 章 D-14；`yaml:runtime.decision_implies_not_invoked=false`。

## CT-Q-15

**问题**：Runtime 不支持 C2 时如何降级？

**裁决**：决策关闭，细节延后。capability gate + version-scoped evidence 原则冻结：Runtime 能力必须按版本化实证声明，未被证实的能力不得夸大；具体降级矩阵细节归 RTE conformance（Track C）。

**依据**：09 章 R16（Runtime pin 能力夸大）；06 章 RTE 接线；08 章 Track C。

## CT-Q-16

**问题**：Context rewrite 不支持时是否仍安全？

**裁决**：是。Context compartment 是软边界（纵深防御），其安全性独立于 runtime 是否支持 context rewrite；硬 backstop 是 Capability/RTE（Phase O1/O2）。SDK 不可靠不推翻隔离模型。

**依据**：09 章 D-06；不变量 CT-F0-11；03 章 Phase O1/O2。

## CT-Q-17

**问题**：request digest 如何 backward-compatible？

**裁决**：遵守 `canonical_request_dump` 向后兼容纪律：新增 optional 字段不改变旧 shape 的 digest；digest 漂移属高风险项，additive field 必须显式验证兼容。

**依据**：01 章 §19；09 章 R17。

## CT-Q-18

**问题**：Shadow 何时进入 Limited Enable？

**裁决**：DEFERRED-by-gate。门控标准指向 INT-PR-04 DoD 五条件（feature_flag、rollback、divergence_diagnostics、fixed_regression、runtime_receipt_closure，见 `yaml:rollout.limited_enable_requires`）；具体时点不在冻结期定死，由门控证据驱动。

**依据**：08 章 INT-PR-04 DoD；`yaml:rollout`；07 章 Shadow → Limited Gate。
