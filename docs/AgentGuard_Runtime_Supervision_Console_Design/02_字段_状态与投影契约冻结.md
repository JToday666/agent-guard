# 02 — 字段、状态与投影契约冻结

## 1. 契约定位与单一事实源

本章冻结 Dashboard 的展示契约，不创建新的后端事实宇宙，也不维护第二套执行轨迹语义。

```text
后端事实
AuditEvent + Approval + Provenance + State/Snapshot + RuntimeOutcomeReceipt
                         ↓
现有唯一执行投影 buildExecutionTrace()
                         ↓
ExecutionTraceViewModel（Graph / List / Inspector 共用）
                         ↓
本章只增加 source/authority、四层依据、Context/Provenance 展示装饰
```

冻结规则：

1. `buildExecutionTrace()` 继续唯一决定步骤聚合、主 policy audit、审批和 outcome 关联；
2. Graph、List、Inspector 必须消费同一批 `ExecutionTraceViewModel.steps`，不得分别重算；
3. 新 projector 只能增加布局、标签、证据引用和有界详情，不能覆盖既有 decision/approval/outcome；
4. 若未来必须替换执行投影，应在一个原子 PR 中迁移三种消费者并保留兼容 adapter，不能长期双写；
5. 内容和因果关系由现有 Provenance ViewModel 承载，执行图边仍只表达审计顺序。

### 1.1 分阶段版本

CORE、CT 或 RTE 的领域契约版本。

## 2. 四层事实不可合并

一个动作至少有四层互相独立的事实：

| 层          | 例子             | 能证明什么                   | 不能推出什么          |
| ----------- | ---------------- | ---------------------------- | --------------------- |
| Decision    | official `deny`  | 当前权威策略不授权           | Runtime 一定没有调用  |
| Approval    | `allow_once`     | 人对本次审批主体作出单次决议 | 动作已开始或成功      |
| Enforcement | `binding_failed` | 执行前约束未满足             | 已有 terminal receipt |
| Execution   | `not_invoked`    | Runtime receipt 记录未调用   | 整个 Trace 已终止     |

```text
DENY != BLOCKED != NOT_INVOKED
ALLOW != STARTED != EXECUTED
ASK + ALLOW_ONCE != ALLOW
FAILED != NOT_INVOKED
```

任何通用节点颜色都不得承担这四层的“合并最终状态”。动作卡片必须分别显示四个 badge 或
四个子区块。

### 3.3 Mock 和 mutation 硬门

数据源模式不是页面、路由或 Fixture 可以自报的字符串，而是数据源工厂创建时给出的不可变
描述符：

```ts
export type DashboardDataSourceDescriptor = Readonly<{
  readonly owner: "dashboard_data_source_factory";
  readonly dataSourceMode: DataSourceMode;
  readonly buildProfile: "production" | "development" | "test";
  readonly capabilities: Readonly<{
    readonly approvalMutation: boolean;
    readonly localReplayImport: boolean;
    readonly syntheticFacts: boolean;
  }>;
}>;
```

- production factory 只能构造 `live_api`，不能 import Mock/Replay/Hybrid provider；
- development/test factory 可显式选择其他 provider，且模块必须 dev/test-only、lazy loaded；
- URL、响应 payload、Fixture 和页面组件只能**降级为只读**，不能把 mode/capability 升级；
- CI 必须检查 production bundle 不含 Fixture、local replay importer 或 Hybrid provider。

TypeScript `readonly` 不是运行时安全边界。factory 必须同时 `Object.freeze()` descriptor 和嵌套
capabilities；descriptor 不接受调用方输入，也不从 API/route 反序列化。provider/store 私有持有
该对象，页面只读 getter；运行时冻结失效、owner/profile/mode 组合非法或对象被替换时 fail closed
为 `approvalMutation=false`。

```text
dataSourceMode != live_api OR temporalState != following
=> 整页只读
=> 不显示可执行 resolve 控件
=> 深链到 approval 详情时继续携带 readonly=1
```

即使为 `live_api + following`，也必须确认 approval、action、official decision 和 basis 都来自
Live、唯一关联同一 `trace_id`，才允许 mutation。Historical 默认只读；Pure Mock 使用页级
水印；Hybrid 逐元素显示来源。

该判定必须在 data-source/store 的 mutation boundary 与 UI 使用同一个 selector；隐藏按钮不是
安全边界，`readonly=1` 也只是 defense-in-depth：

```ts
export interface ApprovalMutationContext {
  targetApprovalId: string;
  approvalId: string;
  basisApprovalId: string;
  temporalState: TemporalState;
  readonlyOverride: boolean;
  sessionAuthenticated: boolean;
  csrfReady: boolean;
  approvalStatus: "pending" | "settled" | "unknown";
  traceId: string;
  approvalTraceId: string;
  actionTraceId: string;
  officialDecisionTraceId: string;
  basisTraceId: string;
  actionId: string;
  basisActionId: string;
  officialDecisionId: string;
  basisDecisionId: string;
  policyAuditId: string;
  basisPolicyAuditId: string;
  officialDecisionValue: "allow" | "ask" | "deny" | "unknown";
  approvalSource: ElementSourceMode;
  actionSource: ElementSourceMode;
  officialDecisionSource: ElementSourceMode;
  basisSource: ElementSourceMode;
}

// 仅由 data-source factory/store 模块内部创建；descriptor 不由页面传入。
function createApprovalMutationSelector(
  descriptor: DashboardDataSourceDescriptor,
): (c: ApprovalMutationContext) => boolean {
  return (c) =>
    descriptor.dataSourceMode === "live_api" &&
    descriptor.capabilities.approvalMutation &&
    c.temporalState === "following" &&
    !c.readonlyOverride &&
    c.sessionAuthenticated &&
    c.csrfReady &&
    c.approvalStatus === "pending" &&
    c.officialDecisionValue === "ask" &&
    [
      c.targetApprovalId,
      c.approvalId,
      c.basisApprovalId,
      c.actionId,
      c.basisActionId,
      c.officialDecisionId,
      c.basisDecisionId,
      c.policyAuditId,
      c.basisPolicyAuditId,
      c.traceId,
    ].every((id) => id.length > 0) &&
    c.targetApprovalId === c.approvalId &&
    c.approvalId === c.basisApprovalId &&
    c.actionId === c.basisActionId &&
    c.officialDecisionId === c.basisDecisionId &&
    c.policyAuditId === c.basisPolicyAuditId &&
    [
      c.approvalTraceId,
      c.actionTraceId,
      c.officialDecisionTraceId,
      c.basisTraceId,
    ].every((id) => id === c.traceId) &&
    [
      c.approvalSource,
      c.actionSource,
      c.officialDecisionSource,
      c.basisSource,
    ].every((source) => source === "live");
}
```

页面只把实际 `targetApprovalId + decision` 交给 store，不能提交 mutation context。store 从自己
的当前索引重新读取 pending Approval、所选 action、official decision、policy audit 和 basis，
构造 context，暴露同一 selector 的只读结果供页面呈现，并在实际 `POST` 前再次检查。任何失败
都返回本地 `mutation_not_permitted`，绝不调用网络。服务端仍独立执行 session、CSRF、状态和
授权校验；提交竞态由 409 收敛。

### 6.2 确定性映射

| 源事实                                                              | certainty 上限 |
| ------------------------------------------------------------------- | -------------- |
| complete + 稳定 ID/refs + exact + observed/deterministic            | confirmed      |
| complete + strong，或 partial + exact/strong                        | supported      |
| complete/partial + possible，或任何 semantic_inferred               | possible       |
| stale/unknown/not_applicable、legacy causal、缺引用/端点/版本或冲突 | unknown        |

多个 possible 不得累加为 confirmed。内容进入模型上下文只有明确 `assembled_into`、等价
关系证据，或 receipt 明确 `tool_result_entered_context=true` 时才能显示 confirmed。
`not_applicable` 不显示 CT 因果结论；partial/stale 不能仅靠多条边升级。

## 7. Context Manifest Evidence（CT-PR-04-M TARGET）

### 7.1 目的和 producer

正式 `ContextAssemblyPlan` 是 ephemeral，CT-PR-04 原 DoD 并未冻结持久化 Manifest。
`CT-PR-04-M` 必须在组装时生成专用 `bounded_context_manifest_envelope`；不能复用会静默截断
数组的 generic evidence redaction，也不能由前端事后重建完整 prompt。

权威 producer 只允许 Guard API 内部 `CT Context Builder → record_context_manifest()`；普通
Adapter 的 `event:audit:write` **无权**生产该语义。实现必须新增严格
`ContextManifestAuditRecord/ContextManifestEnvelope(extra=forbid)` 分支：

- 外部 `POST /v1/audit/events` 遇到保留的
  `runtime_observation/context_manifest_recorded` 直接 403/422；不能因同名 event 获得 Manifest
  语义；
- 内部 writer 从已验证 ContextChunk/SourceFact 派生 trust/fact_authority/taints/counts，校验
  Trace/scope/links，不接受 Adapter 自报升级；
- `metadata.producer=guard_api_context_builder` 和 `producer_binding_id` 由服务端注入并纳入摘要；
- `sanitize_audit_event()` 在 generic `redact_structure` 前摘出 `evidence.context_manifest`，走
  专用 strict validate → field-aware redact/bound → JCS digest → typed budget 通道，再回填；
- 专用通道只处理 `content_preview` 等允许降级字段，必须保留 `sensitive:boolean`、sequence 和
  EvidenceRef 的类型；禁止 generic `sensitive → "[redacted]"` 或 nesting limit 破坏 schema；
- 回填后再次 strict validate 并核对 canonical digest。全局预算不足时整块变为明确
  BudgetDroppedRef，不做数组/嵌套静默截断。

## 9. Runtime Outcome 证明规则

codes；该 strict ref 本身位于同一 policy Audit，Dashboard 通过父 Audit locator 定位，不新增悬空
eligibility record。

### 10.3 Rollout head、CAS 与时序冻结

配置事实只追加 revision，不原地更新；`RolloutHeadV1` 只是 Guard API 的 per-rollout 并发索引：

空存储的逻辑 genesis 固定为
`RolloutCatalogHeadV1(epoch=0, catalog_digest=sha256(UTF8("[]")), updated_at=null)`；即使后端延迟
materialize，也必须返回这组相同语义。首个 initialize command 的
`expected_catalog_epoch/digest` 必须逐字等于 genesis，且 `expected_revision/rollout_digest` 为 null；
成功时在同一事务推进 catalog epoch 1、写入非空 `updated_at` 和首个 rollout head。此后每次成功
mutation 恰好 `epoch+1`；Memory/PostgreSQL/restart 均不得重置已有 catalog epoch。

```text
RolloutMutationCommand(mutation_id, command_digest, expected head)
  → optional fast lookup (rollout_id, mutation_id)
  → fast same command digest: return original persisted revision
  → fast different command digest: conflict
  → no fast hit: acquire rollout-routing catalog exclusive lock
  → lock current RolloutHead
  → mandatory second lookup (rollout_id, mutation_id) while holding the lock
  → locked same digest: return original; locked different digest: conflict
  → still no record: exact catalog + head CAS check
  → validate no overlapping official route; derive next catalog epoch/digest
  → validate/bound/digest new append-only V21RolloutAuditRecord
  → append config audit + CAS RolloutHead + catalog head in one transaction
```

- `command_digest = sha256(JCS(command excluding command_digest))`；`mutation_id` 由受信控制面生成，
  在 rollout 内唯一；
- 丢响应后的 exact retry 先命中 mutation record，返回原 revision/config audit/effective_at，不重新
  生成服务端时间；同 mutation ID/异 command digest 返回 409；首次并发都 fast-miss 时，后取得
  lock 的请求必须二次 lookup，不能把同 key/同 digest 错报 stale head；
- 只有没有 replay 命中时才检查 expected catalog/head；任一 stale 返回 409，不产生 config audit；
- `effective_at` 由服务端事务时间生成，v1 不接受未来 scheduled activation；
- rollback 也必须 CAS 当前 head，并追加一个新的 `mode=shadow` revision；
- Memory 用 routing RW lock + per-rollout lock，PostgreSQL 用同一事务中的 shared/exclusive catalog
  advisory lock + rollout row/advisory lock；两种后端语义一致；
- config audit 写入成功但 head 未更新、或 head 更新但 audit 未持久化，均属于事务失败，不能对外
  可见；
- `RolloutHead/RolloutCatalogHead` 不进入 Dashboard、不作为第二事实源；可审计事实仍是 append-only
  config audit，Trace 使用当次 policy ref。

catalog 只包含有界 routing descriptor：rollout ID/revision、mode、scope identity、runtime/profile、
policy revision/digest 和 cohort revision/digest；不包含 Secret、完整 roster 或 rollout digest。
`catalog_digest = sha256(JCS(sorted routing descriptors))`，因此不与包含该值的 `rollout_digest`
形成循环。initialize/enable/update/promote/rollback 都在同一事务推进 catalog epoch；已知 cohort
roster 展开后出现 official scope 重叠时，mutation 直接冲突，不靠前端选择优先级。

唯一锁序冻结为：

```text
rollout-routing catalog lock（evaluation=shared；mutation=exclusive）
→ per-rollout lock(s)，按 rollout ID 升序
→ policy_evaluation/event lock
→ audit_integrity/audit-chain lock
→ provenance lock
→ approval lock
→ memory_change lock
→ action_critic lock
```

Memory 必须由新 wrapper 先取 routing shared/exclusive lock，再取 per-rollout lock，之后才进入现有
`evaluation_transaction()`；禁止已经持有 audit/provenance lock 后反向获取 catalog/rollout lock。
rollout mutation 可跳过不需要的中间锁，但不能逆序。

PostgreSQL 在最外层事务首先获取 catalog shared/exclusive transaction advisory lock，再按 ID 获取
rollout-scoped advisory/row locks，之后才写 audit/provenance/approval 等表；禁止在已有 evaluation
transaction 内开启 nested transaction 或后取 advisory lock。Memory/PostgreSQL 都必须通过并发
超时测试证明 enable/update/rollback 与 evaluation 无死锁。

evaluation 即使按旧 scope 看不到候选 rollout，也必须先持有 catalog shared lock；该锁一直持有到
policy Audit commit，使 scope expansion/enable 要么线性化在本次评估之前，要么等待本次评估完成。
evaluation finalize 到 commit 的固定过程为：

```text
acquire catalog shared lock; snapshot epoch/digest and resolve candidate rollout IDs
→ lock all candidates by canonical ID; recheck catalog/head while shared lock is held
→ require exactly one matching official rollout（否则 legacy official/V2 shadow）
→ validate case/cohort/runtime/profile/policy/effective_at
→ validate current snapshot against configured schema/projector/eligibility gate
→ validate tightening-only transition + enabled path + rule ownership transfer
→ derive bounded v21_rollout_ref from exact catalog + head/config revision
→ finalize official decision + commit policy Audit atomically
→ release lock / commit CAS check
```

TARGET 中 server-internal `policy_evaluation` 的 `AuditEvent.timestamp` 冻结为
`evaluation_commit_at`：它必须在 catalog/rollout/evaluation 锁内、Audit append 之前由服务端生成，
不得复制 GuardEvent 输入时间，也不得被 Adapter/request 覆盖。backend 与 Dashboard 都使用该同一
wire 字段判断 `effective_at <= AuditEvent.timestamp < attestation.expires_at`；不新增仅数据库可见的
`ingested_at` 作为 official 条件。

若 head revision/digest 在提交前变化，旧 ref 不得提交，按 V21-11 冻结语义重试一次受控读取、回退
shadow 或 fail closed。由此保证：rollback commit 之后，不会再出现 commit 时间更晚却引用旧 official
head 的 policy Audit；rollback 之前已经提交的历史 official 记录保持不变。

#### 10.3.1 唯一 official GuardDecision 原子切换

V21-11 不能只把 `decision_v21` 或 rollout ref 标成 official。当前 replay 的唯一权威决策快照是
`policy_evaluation.evidence.guard_decision`，因此 authoritative selection 必须在创建任何审批、
memory change 或 critic review **之前**完成：

```text
legacy GuardDecision + V21 candidate GuardDecision
→ 在 rollout/evaluation transaction 内复核全部 limited-enable Gate
→ select one authoritative GuardDecision
→ 再从该唯一对象创建 approval / memory change / critic review / provenance
→ 原子写 policy Audit + v21_rollout_ref
→ 返回 API response
→ RTE 只消费该 response/decision_id
```

当且仅当 V21 official Gate 全部通过时，V21 candidate 才成为 `authoritative_guard_decision`；否则
继续选择 legacy，V2 保持 shadow。以下位置必须逐字段引用同一个 authoritative object，禁止分别
重算、先用 legacy 建副作用后只改 Audit，或保留双 official：

| 消费者/载体                                    | 必须一致的内容                                                               |
| ---------------------------------------------- | ---------------------------------------------------------------------------- |
| `GuardEvaluationResponse.decision`             | 完整 `GuardDecision`                                                         |
| policy Audit 顶层                              | decision/risk/severity/blocked/reason 与该对象一致                           |
| `evidence.guard_decision`                      | 该对象的完整 canonical model dump；仍是 replay 唯一载体                      |
| `links.decision_id` / Provenance decision node | 同一 `decision_id`                                                           |
| `DecisionEvidenceV21`                          | official 时 `final_decision` 与该对象的 decision 一致；legacy 仍留作诊断字段 |
| Audit metadata                                 | `v21_final_decision_id/digest` 与该对象 ID/canonical digest 一致             |
| Approval / Memory / Action Critic              | 只在 selection 后由该对象产生，关联同一 decision/policy Audit                |
| RTE binding / Receipt                          | 只绑定该 decision ID、policy Audit ID 和目标 action                          |

这些写入与 rollout head 复核属于同一 evaluation transaction。任何消费者无法原子切换、typed
evidence/rollout ref 无法持久化、或事务中途失败时，不能提交“部分 V21 official”；必须整体回滚，
保持 legacy official/V2 shadow，或按冻结 fail-closed 语义返回失败。幂等 replay 必须从
`evidence.guard_decision` 重建与首次 Live 完全相同的 API decision，随后 RTE/receipt 关联也必须
保持同一 decision ID。

### 10.4 专用 sanitizer 与预算

以下内容属于不可被 generic budget/drop 改写的 critical set：

| 记录                        | Critical evidence / metadata                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------- |
| 所有 `policy_evaluation`    | 顶层 decision 字段、`evidence.guard_decision`、`evidence.policy`、metadata `request_digest/policy_digest` |
| V21 candidate 已 finalize   | 上述内容 + metadata `v21_final_decision_id/v21_final_decision_digest`                                     |
| V21 official                | 上述内容 + `evidence.decision_v21`、`evidence.v21_rollout_ref`                                            |
| Rollout config              | `evidence.rollout_v21`                                                                                    |
| Runtime profile attestation | `evidence.runtime_profile_attestation`                                                                    |

服务端必须在 generic `redact_structure/enforce_evidence_budget` 前摘出 critical set，执行 strict
validate → field-aware bound → JCS digest/关联校验 → round-trip validate，再回填；generic sanitizer
不得截断、改型或替换这些 key。`evidence.guard_decision` 继续走现有 GuardDecision typed bound，
`evidence.policy` 的 revision/digest 组合必须完整，不能退化为 `_truncated` commitment。

GuardEvent/Adapter metadata 与 server-reserved metadata 必须先分区：request 携带
`request_digest/policy_digest/v21_final_decision_id/v21_final_decision_digest` 同名键时拒绝，不能覆盖或
占用槽位。producer 先确定性 bound/sort 不受信 metadata 和可选 evidence，再注入固定 reserved keys；
对象 100-key 上限必须为 reserved keys 预留，不得依赖插入顺序。

冻结上限：

| 对象/字段                                       | 上限与行为                                                                                |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------- |
| rollout/runtime/profile/policy/snapshot/rule ID | 本契约内每项 1–96 Unicode 字符；控制字符/Secret pattern 拒绝                              |
| digest                                          | 仅 allowlisted algorithm + canonical bytes，序列化最长 96 字符                            |
| `case_ids`                                      | 最多 32 项、每项 96 字符；cohort mode 必须为空                                            |
| cohort id/revision/digest + membership ref      | cohort mode 必填；绑定不可变 roster，ref 复用 strict EvidenceRef                          |
| `enabled_path_ids`                              | 最多 4 项且只能取冻结 allowlist；policy matched path 必须为其子集                         |
| transferred/matched rule IDs                    | config 最多 32 项、policy ref 最多 8 项，每项 96 字符                                     |
| matched rule ownership refs                     | 最多 8 项，与 unique matched rules 一一对应                                               |
| snapshot eligibility/actual snapshot            | config 只存 gate revision/digest；policy ref 存当次 snapshot + passed/allowlisted reasons |
| `reason_codes`                                  | 最多 16 项、每项 64 字符、allowlist；不接收自由文本                                       |
| `evidence_refs`                                 | 最多 8 项，复用正式 EvidenceRef 长度/类型校验                                             |
| `rollout_v21`                                   | canonical JSON 最大 24 KiB；超限则整个配置事务失败                                        |
| `v21_rollout_ref`                               | canonical JSON 最大 12 KiB；超限则不得提交 V21 official policy Audit                      |
| `runtime_profile_attestation`                   | canonical JSON 最大 4 KiB；超限则不产 attestation/ref，评估只能 shadow                    |
| policy evaluation critical set                  | 必须在 Audit 64 KiB 总预算内完整 round-trip；不能替换为 generic truncated ref             |

`rollout_digest` 必须在 field-aware bound **之后**，对排除自身的最终 `rollout_v21` 计算；policy
ref 复制已持久化 config revision 的 digest，不对 subset 另算。policy writer 必须先为顶层 decision、
`guard_decision + policy + reserved metadata` 预留预算；V21 official 再原子预留
`decision_v21 + v21_rollout_ref`，最后才按既有优先级降级 request-controlled metadata、preview、
GuardEvent 投影和其他可选 evidence。

若 critical set 仍无法在 64 KiB 内 strict round-trip，evaluation transaction 必须整体失败且不得返回
可执行 decision/RTE release。特别是：请求方不能通过 metadata flooding 或 evidence 体积压力让本应
收紧的 V21 candidate 静默回退为 legacy allow；这类持久化失败走显式 fail-closed service failure，
不能 generic-drop ref/guard_decision 后继续成功响应。

`case_ids/enabled_path_ids/transferred_rule_ids/matched_path_ids/matched_rule_ids/reason_codes` 是
set-like：producer 按 Unicode code-point 升序输出，validator 拒绝重复；EvidenceRef 按
`(kind, record_type, record_id, json_pointer, ref_id)` 排序并拒绝重复 `ref_id`。先完成排序/去重
校验，再计算 command/rollout digest。total JSON byte limit 优先于单字段上限；超总限直接拒绝，
不静默截数组。`revision/rollout_revision/routing_catalog_epoch >= 1`，catalog head epoch 和
`state_version >= 0`；所有 timestamp 都必须是
RFC3339 UTC（`Z`），非规范格式拒绝。

## 12. URL 与选择契约

不新增 `execution_layer=content`；内容关系留在 Provenance。继续复用现有 query：

```text
view=execution|provenance|audit
execution_layout=graph|list
action_id=<real action id>
node_id=<real provenance node id>
event_id=<real event id>
readonly=1
```

- URL 永不保存 synthetic node ID；
- execution 视图优先 `action_id > event_id`；
- provenance 视图优先 `node_id > action_id > event_id`；
- audit 视图优先 `event_id > action_id > node_id`；
- Content/Context 摘要跳转使用 `view=provenance&node_id=<真实 node id>`；
- Preview/Replay/Hybrid 跳审批详情必须传播 `readonly=1`。
