# AgentGuard Adapter 鉴权方案

## 1. 边界

每个 `runtime + agent_id` 使用独立、不可推导的 adapter credential。Guard API 只保存 token 的 SHA-256 hash、主体、运行时身份、固定 scopes、签发时间、可选过期时间和撤销时间；原始 token 只在签发响应中出现一次。

Adapter 通过 `Authorization: Bearer <AGENTGUARD_ADAPTER_TOKEN>` 调用 Guard API。`AGENTGUARD_ADAPTER_TOKEN` 是 Adapter/Plugin 的消费端配置，不是 Guard API 接受的静态服务端密码。Guard API 不从环境变量注册 adapter token，也不接受未入库的共享 token。

Adapter 不使用 browser session、CSRF token 或 launch code，不能批准自己的请求，也不能读取 Dashboard/CLI 管理接口。

## 2. 签发与配置

先配置 `AGENTGUARD_CONTROL_TOKEN` 和数据库并启动 Guard API，再由控制端签发凭证：

```bash
uv run agentguardctl credential issue --runtime openclaw --agent-id main
uv run agentguardctl credential issue --runtime langgraph --agent-id langgraph-demo
```

`--principal-id` 默认采用 `<runtime>:<agent-id>`；需要限时凭证时可传 RFC 3339 格式的 `--expires-at`。命令只在本次输出中展示完整 token：

```text
Credential: cred_xxx
Runtime: openclaw
Agent: main
Token (shown once): agt_xxx
```

把对应 token 写入该 Adapter 的本机环境或受控密钥存储：

```env
AGENTGUARD_ADAPTER_TOKEN=agt_xxx
```

不得把同一 token 复制给不同 runtime 或 agent。可通过以下命令查看元数据和撤销凭证；列表接口永不返回 token 或 token hash：

```bash
uv run agentguardctl credential list
uv run agentguardctl credential revoke <credential_id>
```

轮换采用“签发新凭证 → 更新消费端 → 验证心跳和评估 → 撤销旧凭证”的单一路径。

## 3. 固定权限

所有活动 adapter credential 使用服务端固定 profile，调用方不能自选角色或 scopes：

```text
event:evaluate
event:audit:write
approval:wait
adapter:status:write
```

| 接口                                      | Scope                  |
| ----------------------------------------- | ---------------------- |
| `POST /v1/guard/evaluate`                 | `event:evaluate`       |
| `POST /v1/config-audit/evaluate`          | `event:evaluate`       |
| `POST /v1/audit/events`                   | `event:audit:write`    |
| `GET /v1/approvals/{approval_id}/wait`    | `approval:wait`        |
| `PUT/POST /v1/adapters/{runtime}/...`     | `adapter:status:write` |

Adapter 不具有 `approval:resolve`、`auth:launch`、`audit:read`、`metrics:read`、`trace:read`、`policy:read`、`credential:*` 或其他管理权限。

## 4. 身份绑定

Bearer 校验成功后，Guard API 从数据库恢复 `principal_id`、`runtime` 和 `agent_id`，并在业务写入前校验请求身份：

- GuardEvent 的 `runtime` 和 `security_context.agent_id` 必须与凭证一致；
- ConfigAuditEvent 的 `runtime` 和 `metadata.agent_id` 必须与凭证一致；
- adapter status/heartbeat 的凭证 runtime 必须与路径 runtime 一致，载荷 `agent_id` 必须与凭证一致；载荷不重复传 runtime，`runtime_id` 仅表示具体运行实例；
- approval wait 必须同时匹配创建审批的 principal、runtime 和 agent；
- AuditEvent 必须匹配 runtime；若回执提供 `metadata.agent_id`，还必须匹配 agent。

这样 token 泄漏后的权限被限制在一个明确的 runtime/agent 身份内，不能改写其他适配器的状态或等待其他主体的审批。

## 5. 失效与错误

| 场景                         | 响应                               |
| ---------------------------- | ---------------------------------- |
| 未提供 Authorization         | `401 AUTH_MISSING`                 |
| Bearer 格式、token 无效/过期 | `401 TOKEN_INVALID`                |
| Scope 不足                   | `403 SCOPE_DENIED`                 |
| 请求缺少 agent 身份          | `403 EVENT_IDENTITY_INCOMPLETE`    |
| runtime 或 agent 不匹配      | `403 RUNTIME_IDENTITY_MISMATCH`    |
| 凭证记录身份不完整           | `403 CREDENTIAL_IDENTITY_INCOMPLETE` |

撤销即时生效。Authorization header、完整 token、token hash 不得出现在日志、审计事件、Dashboard、前端环境或导出产物中。

## 6. 不在当前范围

当前不提供适配器登录、Dashboard 凭证管理 UI、OAuth、JWT、mTLS、多租户或远程身份联合。远程部署必须额外使用 TLS、网络访问控制和外部密钥管理。
