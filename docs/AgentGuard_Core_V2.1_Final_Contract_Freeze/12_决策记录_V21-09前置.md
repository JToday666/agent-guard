## D2：state_delta_v21 信封——audit evidence 只存投影身份引用

### 决策

承接 `11_决策记录_V21-08前置.md` D4 第 3 项（`state_delta_v21` 信封归属 V21-09、
随投影记录存储），正式裁决落点与形状：

1. `AuditEvent.evidence.state_delta_v21`（`contract_freeze.yaml` L85
   `state_delta_evidence_location`）信封（版本信封形状同 07 §10，L380-398；
   01 §28，L1151-1160 信封范式）**只存投影身份引用**：
   `projection_id`（幂等键身份，对应 `contract_freeze.yaml` L53
   `idempotency_key_fields`：scope_digest / source_record_type / source_record_id /
   source_revision / projector_version）、`delta_digest`、source identity
   （source_record_type / source_record_id / source_revision）；
2. **全量 delta 本体随 `projection_records` 存储**（投影层既有通道），不内嵌进
   audit evidence；
3. 引用键经 typed bound 通道写入并受 64 KiB evidence 预算约束，预算吃紧时记
   dropped-reference 留痕（仿 `decision_v21` 通道，`11_决策记录_V21-08前置.md` D4
   禁静默丢弃语义），不放宽全局预算。

### 背景

`decision_v21` 与 `state_delta_v21` 同存于同一条 policy_evaluation 审计记录，受
guard-api `enforce_evidence_budget` 64 KiB 预算约束（`apps/guard-api/guard_api/
services/evidence.py` L257）；Postgres 审计写入持全局 advisory lock 串行化，全量
delta 内嵌会直接抬高锁持有时间（写放大）。身份引用足以让离线 divergence/溯源
分析从 `projection_records` 反查全量 delta，证据链不断。

### 否决的替代

**全量 delta payload 内嵌 audit evidence**：冲击 64 KiB 预算并拉长全局审计锁持有
时间（`11_决策记录_V21-08前置.md` D4 背景已警示）；否决。

### 状态

**已冻结**（IMPLEMENTATION 级；信封键属 07 §10 L380-383 已列出的

## D4：四段式事务边界——Phase A 事务外只读 / Phase B 短事务 / Phase C 事务后投影

### 决策

V21-09 Guard API 编排（完整方案 §15，L3201-3211）裁决为**四段式**：

1. **Phase A（事务外只读）**：scope 解析 → ensure_ready → read_snapshot 得
   snapshot V（含 D3 同源注入 revoked 集）；全部存储往返位于事务之外；
2. **Phase B（短事务 `evaluation_transaction(event_id)`**，现有实现
   `apps/guard-api/guard_api/services/evaluation.py` L120**）**：replay-or-conflict
   幂等 → legacy 链（保持官方，D1）→ 五元组 revalidate（03 §12，L456-462）→
   finalize → audit commit（含 `decision_v21` 与 `state_delta_v21` 引用信封，D2）；
3. **Phase C（事务提交后）**：scope_lock 内 base state 读取 → delta 构造 →
   `project_committed`（复用 `apps/guard-api/guard_api/services/approval.py`
   `_project_allow_once_grant` L270 起的 commit→project 原子化范本，含
   `verify_source_committed` 钩子复核审计记录已落盘，F0-8）；投影失败收敛为
   告警 + dirty（projector 既有语义），绝不影响响应；
4. **event 幂等事务与 state CAS 锁严格分离**：`evaluation_transaction(event_id)`
   只负责请求幂等，state CAS/lock 负责跨事件状态一致性，不得混为一个锁
   （07 §9，L359-364 逐字冻结）；semantic 预留钩子位置恒在事务外（03 §12，
   L454 "transaction 外调用 LLM"、L467 "Semantic 期间不持长锁"）。

本裁决同时**消除 V21-08 S8 已知局限**："shadow I/O 计入 evaluate 事务窗口"
（`reports/v21-08-shadow-overhead-smoke/shadow-overhead-smoke.md` §7 第 2 条，
L87-91："shadow 编排……整体位于 evaluation_transaction 串行事务内，会拉长事务
持有窗口……正式开启前建议评估只读解析前移事务外"）——flag on 切换编排后，
事务窗口内不再有 snapshot/task 存储往返。

### 背景

完整方案 L97-126 顺序冻结：决策 → 生成权威 Record + StateDelta → Commit 成功 →
Projector 幂等应用 committed delta → OnlineSecurityState；committed record 已
成功但投影未应用时 state 标 dirty、必需域缺失禁 CLEAR_ALLOW（L121-126）。07 §9
L351-354 伪代码明示"only after authoritative commit → project_committed"。
四段式是该顺序冻结的最小落地，同时把 semantic outside-tx 位置一次性编排到位，
避免 V21-13 接入时二次重编排。

### 否决的替代

**revalidate/project 全部留在 evaluation_transaction 内**：延续 S8 事务窗口局限
（V21-08 smoke 实测 flag on ΔP50 +16~31ms 上界，postgres 下更明显），且与
07 §9 commit→project 时序张力更大；否决。

**CAS 冲突自动重试**：V21-09 无决策面影响，重试引入风暴风险且 stale digest
重试无收敛保证；否决，fail-closed 收敛留痕，重试策略待 V21-10/11 裁决。

### 状态

**已冻结**（IMPLEMENTATION 级编排裁决；07 §9/§10 与完整方案顺序冻结正文逐字
不动）。

## D7：finalize → GuardDecision 映射口径

### 决策

V21-09 `GuardEngine.finalize`（完整方案 §15，L3194-3198）产出 GuardDecision 的
字段口径逐条冻结如下：

1. **decision**：沿用 `_SHADOW_FINALIZE_MAP`（`decisions/shadow.py` L523-527：
   CLEAR_DENY→deny、DEFER→ask、CLEAR_ALLOW→allow），即 03 §14（L495-522）优先级
   在 semantic=None 下的闭包形态；V21-09 semantic 恒 None（DEFER→ask），
   binding invalid/stale → ask 分支以纯函数钩子预留（03 §14，L508-509）；
2. **risk_score / severity**：由 `disposition × impact` 确定性映射表给出（下表，
   impact 取 03 §4 冻结四级 L67-115；severity 取既有代码词表
   critical/high/medium/low）。`risk_score` **仅兼容用途**（旧 API 兼容 /
   Dashboard 排序 / 人类可读 risk band），不得让 decision 依赖分数阈值
   （03 §15，L526-535 逐字冻结）；severity 同属兼容/展示面。映射表沿两轴单调：

   | disposition \ impact | critical | high | moderate | low |
   |---|---|---|---|---|
   | **CLEAR_DENY** risk_score / severity | 95 / critical | 85 / high | 70 / medium | 55 / medium |
   | **DEFER** risk_score / severity | 80 / high | 65 / medium | 50 / medium | 35 / low |
   | **CLEAR_ALLOW** risk_score / severity | 30 / low | 20 / low | 10 / low | 5 / low |

3. **reason / categories**：由 `assessment.reason_codes`（01 §25，L988）确定性
   派生——reason 为受控 reason code 的规范化拼接，categories 为 reason code
   的域前缀归类；不引入自由文本、不读 wall-clock；
4. **rule_hits**：V21-09 恒为**空表**。理由：`RuleHit` 是 legacy 规则命中形状
   （`decisions/models.py` L62），V2 侧 PolicyViolation（01 §21）有独立身份与
   tier 语义，V21-09 不存在 V2 原生 policy violation producer 可合法产出
   legacy rule 身份；伪造映射会污染 retained regression 口径。PolicyViolation
   证据经证据信封 `policy_violation_ids` 留存（01 §28，L1134）；
5. **decision_id 确定性派生**：`GuardDecision.decision_id` 当前默认
   `new_id("dec")` uuid（`decisions/models.py` L57），finalize **必须显式传入**
   确定性派生 id——仿 `derive_assessment_id` 范式（`decisions/shadow.py`
   L156-171：前缀 + `canonical_sha256` 稳定身份投影，禁 uuid
   default_factory），派生输入为 assessment 身份（`assessment_id` +
   `assessment_digest`，semantic_digest 存在时并入），同输入必同 id
   （T-Replay 锚点语义）；01 §29 L1178 "random UUID 禁入安全摘要"同源口径；
6. **latency_ms**：恒 `None`（`decisions/models.py` L66 可空字段），禁止
   wall-clock 计算——replay 确定性要求同输入同产物（01 §29，L1177 wall-clock
   latency 禁入摘要的同源纪律）。

### 背景

finalize 产物在 V21-09 只进证据信封与权威记录（D1），但 GuardDecision 是公开
兼容契约（`contract_freeze.yaml` L82 `guard_decision_breaking_change_required:
false`），字段形状不动、取值口径必须先行冻结，否则 uuid/wall-clock 默认值会
破坏审计可复算性与 replay 确定性。

### 状态

**已冻结**（IMPLEMENTATION 级；GuardDecision 模型逐字不动，映射表与派生口径
属 finalize 实现的取值收敛，T1 契约测试断言同输入同产物）。

## D8：revalidation stale 的 divergence 归类——新增受控类目 degraded_stale_judgment

### 决策

1. Phase B 五元组/state version revalidate（03 §12，L456-463）返回 stale 时，
   该事件的 `divergence_category` **新增受控类目
   `degraded_stale_judgment`**——取代九宫格值（降级优先语义同
   `11_决策记录_V21-08前置.md` D2 两个既有降级类目：shadow 无法产出可信
   disposition 时不得静默归入九宫格）；
2. 同步扩展 `decisions/divergence.py` 封闭词表（L54-55 降级类目常量、
   L71-78 `DIVERGENCE_VOCABULARY` 全集、L95 起 `classify_divergence` 穷尽
   映射）：新类目以常量逐字登记，映射函数对全部 3×3 + 3 降级类目穷尽，
   出现未定义组合仍抛 `DivergenceVocabularyError`（L81-82，fail-closed，
   **不得自造新词**）；
3. stale 同时记 `EvaluationDegradation`（01 §22，L907-916 `failure_kind` 枚举
   已含 `"stale"`，无需新增枚举值）并计入证据 `degradation_ids`，V21-09
   权威提交按 T2 口径放弃（legacy 不受影响）。

### 背景

11-D2 冻结的 `degraded_component_failure` 语义是"shadow 组件异常"（ActionIR /
fusion 求值 / snapshot 读取故障），而 revalidation stale 是"评估本身成功、但
提交时点上下文已漂移"——归因与整改措施不同（组件故障 vs CAS 竞争），V21-10
pre-enable gate 的 shadow divergence 分析（完整方案 §16，L3225）需要机器可
区分两类，否则 stale 高发会被误读为组件可靠性问题。新增受控类目保持归因
可解释性，代价仅是词表常量一处同步扩展，封闭性与 fail-closed 语义不变。

### 否决的替代

**归入 degraded_component_failure 语义扩展**：无需动词表，但混淆"组件故障"与
