# 创新性说明

AgentGuard 面向工具增强型 LLM Agent 的运行时安全问题，提出了一条以工程闭环为核心的安全监督路线。作品并未将创新建立在新的基础模型训练之上，也没有把规则系统包装为不可解释的智能判定，而是围绕 Agent 真实运行过程中的工具调用、上下文组装、模型输入输出、记忆写入和消息发送等行为，构建了从事件建模、策略判定、资源一致性检查、审计留证到副作用评测的完整链路。与仅在文本输入或最终回答上做审查的方案相比，AgentGuard 更关注模型获得工具能力后对外部环境产生的实际影响，并将这些影响转化为可以被描述、被判定、被追踪和被复核的工程对象。

从整体结构看，AgentGuard 的创新主线主要体现在四个方面。第一，系统以 `GuardEvent` 为统一事件契约，把不同运行时中的关键行为抽象为标准化安全事实，使检测器、策略和评测框架能够围绕同一语义工作。第二，系统采用“一核两壳”的监督架构，将无状态监督核心与 LangGraph、OpenClaw 两类运行时适配器解耦组织，使安全判定逻辑不绑定单一 Agent 框架，并具备向更多智能体框架扩展的基础。第三，系统将每次安全判断沉淀为审计记录和 provenance graph，通过 audit hash chain、事件节点、决策节点、审计节点和复盘关系，把一次性阻断扩展为可验证的证据链。第四，系统以 AttackBench 对文件外泄、消息外发、记忆污染、工具劫持和 Agent 滥用等真实副作用进行组织和评测，使作品的安全能力不只停留在演示层面，而能够进入可复查、可迭代的实验框架。

在能力边界上，AgentGuard 始终以当前已实现的工程系统为依据。系统关注运行时行为治理，不替代业务系统自身的身份认证、权限管理、沙箱隔离和密钥管理；当前检测器以确定性规则、策略配置和启发式匹配为主，不使用外部 LLM、embedding 或训练新模型完成语义判断。这样的取舍使系统具备低依赖、可解释和易复现的特点，也要求报告中对复杂跨轮语义攻击、模型供应链风险和未知攻击手法保持克制表述。

## 4.1 GuardEvent 驱动的运行时行为建模机制

传统大模型安全防护通常从文本入口或文本出口入手：在用户输入进入模型前进行过滤，或在模型回答返回用户前进行审查。这类方式对纯问答系统具有一定价值，但面对工具增强型 Agent 时存在天然不足。Agent 的风险不一定出现在最终回答中，而可能隐藏在执行路径中：模型可能先读取本地文件，再调用邮件工具外发；可能把网页中的间接指令写入长期记忆；也可能在工具描述被污染后调用与用户任务不一致的高风险接口。如果安全系统无法统一描述这些运行时行为，就很难在副作用发生前作出有效判断。

AgentGuard 的第一项工程突破，是将 Agent 运行时行为统一抽象为 `GuardEvent`。系统没有把安全逻辑硬编码在某一个工具函数或某一个框架回调中，而是先定义跨 runtime 的事件契约，再由 LangGraph、OpenClaw 等适配层把原始工具调用、上下文、模型输入输出、工具结果、记忆写入和消息发送转换为标准事件。当前 Core 中的 `GuardEventType` 覆盖 7 类关键节点，使不同运行时的安全事件能够进入同一套判定流程。这种设计相当于为 Agent 行为建立了统一的工程语言，解决了多框架、多工具、多攻击路径下安全逻辑难以复用的问题。

`GuardEvent` 的关键价值不只是统一字段名称，而是将安全判断所需的事实前置到结构化事件中。`trace_id` 将一次行为绑定到可复盘的调用链，便于后续从事件追踪到决策、审计和证据展示；`pre_execution` 标明事件是否发生在副作用之前，使系统能够区分执行前拦截与事后观察；`security_context` 承载用户任务、来源可信度、上下文来源等判断依据；`payload` 则根据事件类型绑定到对应结构化模型，避免检测器从自然语言日志中猜测工具名、参数或资源目标。通过这些字段，系统把“模型可能要做什么”转化为“某个运行时在某条 trace 中提出了一个可验证的行为事件”。

这种事件契约使 AgentGuard 具备较强的跨运行时适配能力。对于 LangGraph，系统可以在工具节点执行前生成 `tool_call_proposed` 事件，并根据判定结果决定是否继续调用真实工具；对于 OpenClaw，hook-only 插件可以将工具调用、消息发送、安装配置和工具结果观察映射为标准事件；对于 AttackBench，离线样本也可以通过同一事件结构进入 Core 判定。不同入口共享同一个事件模型，意味着安全判定不再依赖某个框架的内部对象，也不需要为每一种 runtime 重写检测器。

在事件建模基础上，AgentGuard 进一步采用无状态判定内核。`GuardEngine.evaluate()` 每次只接收当前 `GuardEvent` 和 `PolicyBundle`，顺序运行默认检测器，并将所有检测结果合并为最终决策。Core 不直接读写数据库，不创建审批记录，不写审计日志，也不承担前端展示职责；策略管理、审批流、审计入库、指标存储和 trace 查询由 Guard API / Control Plane 负责。这种职责划分使 Core 保持纯粹：给定事件和策略，输出可解释的安全决策。

无状态 Core 带来的直接收益是可复用和可复现。同一套 `GuardEngine.evaluate()` 可以同时服务在线 API、离线 AttackBench 和本地规则核验；同一个事件在同一个 `PolicyBundle` 下能够复现相同判定；检测器的增删和策略覆盖也不会影响审批、审计或 Dashboard 的存储结构。这一点使 AgentGuard 不只是单个 demo 中的一组拦截逻辑，而是形成了可以被扩展、被回归测试、被跨环境复用的安全判定内核。

AgentGuard 还在事件层引入了工具资源语义。工具增强型 Agent 的风险往往不取决于工具名称本身，而取决于工具访问的资源、操作方向和目标对象。系统通过 `ToolProfile` 描述工具类别、类型、允许操作和数据方向，再由 `derive_resources()` 从事件 payload 中派生规范化资源。文件读写、邮件发送、API 请求、代码执行、长期记忆写入、工具结果进入上下文或持久化等行为，都被转换为可比较的资源语义。这样，检测器可以判断实际资源方向是否符合工具画像，也可以识别未画像工具访问 outbound、persistent、execute、write、delete 等高风险资源的情况。

与普通关键词规则相比，资源画像使风险判断更接近 Agent 的真实执行语义。例如，一个标称为读取文档的工具如果派生出 outbound 方向，系统就能够发现工具画像与实际行为不一致；一个未画像工具如果尝试执行本地进程或写入长期记忆，系统可以将其置于人工审批或阻断范围；一个消息发送事件如果目标域名不在可信范围内，检测器可以把外发方向、目标地址和敏感内容共同作为证据。安全判断因此不再局限于“文本是否危险”，而是扩展为“工具能力、资源方向、操作类型和任务上下文是否一致”。

这种 `GuardEvent` 与资源画像结合的设计，形成了 AgentGuard 最核心的工程创新基础。它把分散在不同 runtime 和工具实现中的行为统一为标准事件，把工具能力从自然语言描述转化为结构化画像，把安全规则从单点文本判断推进到行为语义检查。现阶段，系统仍以确定性规则和策略配置为主，对复杂语义改写和长链上下文攻击可能存在覆盖不足；但正因为事件契约清晰，后续引入更强的语义分析、策略学习或组织级权限模型时，可以沿着现有接口渐进扩展，而不需要推翻整体架构。

## 4.2 “一核两壳”的可扩展监督架构

AgentGuard 的第二项工程突破，是采用“一核两壳”的系统设计，将通用安全判定能力与具体运行时接入能力分离。这里的“一核”指无状态的 agentguard-core 监督核心，“两壳”指面向 LangGraph 和 OpenClaw 的两类运行时适配器。核心只接收标准化的 `GuardEvent` 和 `PolicyBundle`，输出 `GuardDecision`，不绑定某一种 Agent 框架、工具注册方式或执行流程；适配器则负责在具体运行时中捕获工具调用、消息发送、上下文构建、模型输入输出和工具结果等行为，并将原生事件映射为统一事件，再根据判定结果执行 allow、deny 或 ask。

这种架构的关键价值在于解耦。传统面向单一框架的安全插件通常把事件捕获、风险判断、执行控制和日志记录混合在一起，一旦迁移到新的 Agent 框架，就需要重新实现大部分逻辑。AgentGuard 将“安全监督核心”与“运行时外壳”分离后，检测器、策略、风险评分、审计证据和评测指标可以集中沉淀在通用层；不同运行时只需要完成事件映射和执行控制，就能复用同一套监督能力。这样，系统不会被某一个 demo、某一种工具节点或某一个 hook 机制锁定。

LangGraph 适配器和 OpenClaw 插件分别体现了两类典型接入方式。LangGraph 侧更接近图式工作流和工具节点包装，适合在工具执行前构造 `tool_call_proposed` 等事件并控制后续调用；OpenClaw 侧更接近 hook 型运行时，通过 `before_tool_call`、`message_sending`、`before_prompt_build`、`llm_input`、`llm_output`、`tool_result_persist` 等关键阶段观察和拦截 Agent 行为。两类适配方式进入 Guard API 后共享同一事件契约和判定接口，说明 AgentGuard 不是绑定单一框架的安全脚本，而是具备跨运行时迁移能力的监督架构。

“一核两壳”也提升了系统的可维护性和可持续迭代能力。当检测器升级、策略规则调整、审计链增强或 Dashboard 展示优化时，改动可以集中发生在核心和控制面，不需要在每个运行时中重复实现；当需要接入新的智能体框架时，新增工作主要集中在适配层，即把新框架的原生事件转换为 `GuardEvent`，并把 `GuardDecision` 转换为对应运行时中的执行控制动作。这种方式使系统具备继续扩展到其他 Agent 框架、工具生态和部署形态的潜力。

需要说明的是，“一核两壳”并不意味着当前系统已经天然覆盖所有智能体框架，而是说明作品在架构上预留了清晰的扩展路径。当前实现通过 LangGraph 和 OpenClaw 两类适配器验证了核心与运行时解耦的可行性；后续若接入 AutoGen、CrewAI、Dify、MCP-based Agent 或企业自研 Agent Runtime，可以沿用“事件映射—统一判定—执行控制—审计复核”的路径渐进扩展。因此，该设计体现了系统通用性、兼容迭代能力和工程生命周期价值。

## 4.3 面向可复核安全治理的证据链工程

Agent 安全系统如果只输出一次 `allow`、`deny` 或 `ask`，并不能充分支撑真实场景中的安全治理。开发者和安全负责人往往还需要回答一系列后续问题：这次事件从哪里来，是否发生在工具执行前，触发了哪些规则，风险理由是什么，是否进入审批，最终审计记录是否连续可信，相关事件之间是否存在因果关系。普通日志虽然可以记录片段信息，但日志格式通常分散在不同组件中，缺乏统一结构和完整性校验，难以支撑系统化复盘。

AgentGuard 的第三项工程突破，是将运行时判定与审计证据链深度结合。系统在 Guard API / Control Plane 中为每次评估构造审计事件，记录原始 `GuardEvent`、决策结果、规则命中、风险分、审批关联和相关元数据。与此同时，系统维护 audit hash chain，为每条审计记录附加 sequence、prev_hash、event_hash 和 canonicalization 等完整性信息。`verify_audit_chain()` 可以按照顺序校验审计链，一旦记录被删除、替换或顺序发生异常，就能够定位首个破坏链条的审计事件。

audit hash chain 的意义在于，它把审计记录从普通数据库行提升为具有连续性约束的证据对象。对于一个运行时防护系统，事后追溯时最怕的问题不是没有日志，而是日志是否可信、是否缺失、是否被局部修改。AgentGuard 通过前后哈希连接，使审计记录在原型系统内具备篡改发现能力。它并不等同于外部可信账本，也不能替代专门合规审计平台，但已经能够支撑作品层面的证据完整性说明，为后续接入签名、归档、外部审计或合规系统提供了清晰基础。

在完整性校验之外，AgentGuard 进一步构建 provenance graph，将一次安全判断的相关对象组织为结构化图谱。系统将 event、decision、audit、action critic 等记录为节点，并通过 `evaluated_to`、`recorded_as`、`reviewed_by` 等边描述它们之间的关系。这样，一次工具调用不只是留下孤立的判断结果，而是能够从原始事件追踪到 Core 决策、审计记录、人工或自动复核信息，并在 Dashboard 的证据页面中形成可浏览的时间线和关系图。

provenance graph 解决的是 Agent 安全中非常关键的因果复盘问题。很多攻击不是单点发生，而是跨越上下文、工具、记忆和消息多个环节：不可信网页可能先污染上下文，再诱导模型调用工具，随后触发消息外发或长期记忆写入。单条日志很难表达这种链路，普通表格也很难展示事件之间的关系。AgentGuard 通过 provenance graph 把“哪个事件被评估为哪个决策”“哪个决策被记录为何种审计事件”“哪个审计事件又被哪个 review 关联”串联起来，使安全人员能够从结果反向追踪原因，也能从输入正向观察风险传播路径。

这一证据链工程使 AgentGuard 的安全能力从“系统做出了判断”推进为“系统能够解释判断并留下可复核证据”。在敏感资源访问场景中，系统不仅能说明某次行为被拦截，还能关联到资源标记、规则命中和 trace；在工具画像不一致场景中，系统可以指出工具类别、资源方向和操作类型之间的冲突；在审批场景中，系统能够把 `ask` 决策、审批记录和后续处理结果连接起来；在评测场景中，系统可以把样本执行结果与具体规则和审计证据对齐。这种证据表达能力，正是工程型安全系统区别于单点规则脚本的重要标志。

与传统事后日志相比，AgentGuard 的证据链更强调结构化、可验证和可展示。结构化体现在事件、决策、审计和复核对象都有明确模型；可验证体现在 audit hash chain 能够发现审计序列中的缺失或篡改；可展示体现在 provenance graph 能够支持 Dashboard 以图谱和时间线方式呈现安全事实。系统不仅考虑“如何拦截攻击”，也考虑“如何证明为什么拦截、如何复盘拦截过程、如何让证据经得起检查”，从而体现出更完整的工程治理思路。

这种设计也保持了现实边界。AgentGuard 当前实现的是原型系统中的本地审计连续性与溯源关系，不将 provenance graph 表述为不可抵赖平台，也不把 audit hash chain 夸大为合规级审计基础设施。它的价值在于为运行时 Agent 安全提供可复核的工程证据框架，使后续扩展到更高强度的签名存储、组织级审计或合规流程时，有明确的数据模型和接口基础。

## 4.4 面向真实副作用的动态评测闭环

Agent 安全评测如果只观察最终回答文本，往往无法准确衡量防护效果。攻击者的目标不一定是让模型说出危险内容，而是诱导模型完成真实副作用：读取并外发敏感文件，向未知地址发送消息，把恶意规则写入长期记忆，调用被劫持的工具，或者执行超出用户任务范围的业务操作。若评测体系只看回答是否拒绝，就可能漏掉已经发生的环境状态变化，也无法说明运行时监督是否真正阻止了危险行为。

AgentGuard 的第四项工程突破，是构建面向真实副作用的 AttackBench 评测闭环。AttackBench 不把样本简单定义为一段攻击文本，而是使用 `AttackCase` 描述攻击类型、输入来源、目标行为、期望决策、成功条件和工具计划。样本中的 `success_condition` 用于刻画攻击是否达成目标，`tool_plan` 用于描述可能触发的工具路径，`target_behavior` 则将攻击意图落到具体行为结果上。通过这样的结构，评测可以围绕“危险行为是否发生”展开，而不是只围绕“回答是否看起来安全”展开。

当前 JSONL 文件可确认共 135 条样本，其中主 AttackCase 数据集 123 条，PoisonedRAG 扩展 12 条。样本覆盖 prompt injection、tool hijacking、memory poisoning、file exfiltration、agent abuse 和 benign 等类型，能够对应工具增强型 Agent 的多个典型风险面。这个规模不被写作防护效果指标，而是说明项目已经具备批量组织攻击样本、正常样本和扩展样本的基础，能够支撑后续在相同 runner 和指标口径下进行复查。

AttackBench 的重要价值在于，它把运行时安全系统的评测对象从文本输出转向环境副作用。文件外泄样本可以检查敏感资源是否被读取并发送到目标地址；消息外发样本可以关注收件人、域名和内容是否符合安全策略；记忆污染样本可以检查特定 namespace/key 是否被写入恶意内容；工具劫持样本可以比较实际工具调用与期望工具画像之间的差异；Agent 滥用样本则可以观察模型是否执行了超出任务需求的高风险动作。这样的评测更贴近 Agent 攻击的真实成功条件，也能更准确地检验执行前拦截和资源一致性检查的效果。

在指标设计上，AttackBench 通过 `calculate_metrics()` 将防御前后攻击成功率、有效样本攻击成功率、阻断率、误报率、正常任务成功率、无效运行比例和指标可信度等维度纳入统一口径。尤其是 `metrics_reliable` 及相关原因字段，可以区分真实可解释结果、无效运行、fake core、allow-all core 或样本不可适用等情况，避免把不可比数据包装为安全效果。对安全评测而言，这种可靠性标记非常重要，因为一次运行失败、样本不适配或基线设置不正确，都可能使指标失去解释价值。

AttackBench 还与 `GuardEvent` 和无状态 Core 形成了闭环。在线运行时产生的事件可以进入 `GuardEngine.evaluate()`，离线评测样本也可以复用同一判定接口；策略版本可以作为评测输入，便于比较不同规则配置下的阻断效果和误报风险；评测结果又可以反向暴露检测器覆盖不足、工具画像缺失或样本设计不充分的问题。这样，AgentGuard 的安全能力不依赖单个演示脚本，而是可以通过样本集合、运行记录、审计证据和指标口径不断迭代。

与一次性演示相比，动态评测闭环更能体现工程价值。单个演示可以证明系统在某个场景下能够拦截某个攻击，却难以说明规则是否过严、是否误伤正常任务、是否能覆盖不同攻击类型、是否能在策略调整后保持稳定。AttackBench 通过恶意样本和 benign 样本并行组织，使系统能够同时关注攻击阻断和正常任务可用性；通过运行质量字段，使无效样本和异常运行不会被混入效果结论；通过样本类型划分，使文件外泄、记忆污染、工具劫持等不同风险可以分别分析。

现阶段，尚未重新运行的 ASR、FPR、延迟和任务成功率不写作既定结论，具体量化数据应以最终测试验证报告为准。AgentGuard 当前能够确认的是评测框架、样本规模、样本模型和指标计算口径已经具备，并且这些能力与运行时事件、策略判定和审计证据链相互衔接。这样的表达既避免夸大实验结果，也突出作品在评测工程上的完整性。

综上所述，本作品的创新性主要体现在工程体系的完整构建上：以 `GuardEvent` 将异构 Agent 行为统一为可判定事件，以 `ToolProfile` 和 `derive_resources()` 将工具能力转化为资源画像和一致性检查，以“一核两壳”将无状态监督核心和 LangGraph、OpenClaw 适配器解耦组织，以 audit hash chain 与 provenance graph 将每次判断沉淀为可复核证据，以 AttackBench 将防护效果拉回真实副作用场景中验证。AgentGuard 没有将自身表述为覆盖所有攻击的通用安全平台，而是在当前可确认实现范围内，形成了一套结构清晰、证据充分、可迁移、可评测、可持续扩展的运行时 Agent 安全监督方案。这种工程闭环既体现了对工具增强型 Agent 风险形态的理解，也展示了从安全理念到系统落地、从单一接入到多运行时扩展的完整路径。
