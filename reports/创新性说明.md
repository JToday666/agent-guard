# 创新性说明

> AgentGuard 面向工具增强型 LLM Agent，在运行时建立可解释、可审批、可审计的行为安全控制面。本章按“问题 → 设计决策 → 源码证据 → 答辩价值”的结构说明创新点，所有表述均以当前源码和已知文档为依据。

## 创新定位

AgentGuard 的创新不是训练新的基础模型，也不是把确定性规则包装成机器学习算法，而是把 Agent 安全的关注点从“模型回答是否安全”推进到“Agent 准备执行的外部动作是否应当发生”。

一句话概括：

> 我们不假设模型永远不会被注入，而是在 Agent 动作产生副作用前建立独立、可审计的控制点。

这一区别非常适合答辩展开：传统文本安全更关注“说了什么”，AgentGuard 更关注“准备做什么、会影响什么资源、是否需要阻断或审批”。

## C1：从文本安全转向行为级运行时监督

### 问题

ReAct、Toolformer 等工作推动了“模型推理 + 工具行动”的 Agent 范式。此类系统的风险不止于生成危险文本，还可能表现为读取文件、调用 API、发送消息、执行命令、写入长期记忆等外部副作用。只做输入过滤或输出审查，难以及时判断某个工具动作是否应当执行。

### 设计决策

AgentGuard 定义 7 类 `GuardEventType`，覆盖当前系统建模的关键行为节点：

| 事件类型                | 关注节点       | 典型风险                           |
| ----------------------- | -------------- | ---------------------------------- |
| `tool_call_proposed`    | 工具调用前     | 敏感资源访问、工具劫持、任务偏离   |
| `context_assembled`     | 上下文组装     | 间接提示注入、污染内容进入上下文   |
| `model_input_prepared`  | 模型输入前     | 未净化的不可信指令进入模型         |
| `model_output_produced` | 模型输出后     | 越狱响应、隐藏上下文或敏感信息泄露 |
| `tool_result_produced`  | 工具结果产生后 | 工具结果污染、持久化污染           |
| `memory_write_proposed` | 长期记忆写入前 | 记忆污染、持久化攻击               |
| `message_send_proposed` | 消息发送前     | 数据外发、敏感内容泄露             |

### 源码证据

`packages/agentguard-core/agentguard_core/events/payloads.py` 定义 `GuardEventType`，`events/contracts.py` 将事件类型绑定到 payload 模型，并对 6 类 raw payload 定义必需字段校验。LangGraph 侧由 `SecureToolNode` / `GuardedToolGateway` 在工具执行前调用 Guard；OpenClaw 侧由 `before_tool_call`、`message_sending` 等 hook 接入 Guard API。

### 答辩价值

这说明 AgentGuard 的防护点不是停留在“模型文本过滤”，而是进入 Agent 行为链路，在副作用发生前做判断。

## C2：事件契约驱动的无状态 Core

### 问题

如果安全规则直接散落在不同 Agent 框架或业务工具代码中，系统会很难复用、测试和审计。不同 runtime 的事件形态不同，也会导致检测逻辑与框架强耦合。

### 设计决策

AgentGuard 将安全判定抽象为稳定接口：

```python
evaluate(event: GuardEvent, policies: PolicyBundle | None = None) -> GuardDecision
```

`GuardEngine` 每次评估只依赖当前 `GuardEvent` 和策略快照，默认顺序执行 10 类检测器，并由 `build_guard_decision()` 合并为 `allow`、`deny`、`ask` 三态结果。

### 源码证据

- `engine.py`：默认注册 `SensitiveResourceDetector`、`ToolHijackDetector`、`OutboundDetector`、`PromptInjectionDetector`、`MemoryPoisoningDetector` 等 10 类检测器。
- `decisions/policy.py`：无触发时返回 `allow`；任一 `deny` 优先输出 `deny`；否则任一 `ask` 输出 `ask`；风险分取最高触发分。
- `policies/models.py`：`PolicyBundle` 承载规则开关、marker、工具画像、外发白名单和规则覆盖配置。

### 答辩价值

无状态 Core 让同一套安全逻辑既能被 Guard API 调用，也能被离线评测复用；事件契约让 LangGraph、OpenClaw 和其他适配器共享同一判定语义。

## C3：工具画像、资源派生与任务一致性联合判定

### 问题

Agent 工具的风险取决于资源、操作和数据流向，而不只取决于工具名称。例如，同样是 API 调用，访问本地 `/status` 与向未知 webhook 发送敏感数据的风险差异很大。

### 设计决策

AgentGuard 将工具调用拆成三层语义：

- **工具画像**：`ToolProfile` 描述工具允许的 categories、kinds、operations、directions。
- **资源派生**：`derive_resources()` 从事件 payload 中派生 file、message、api、process、memory、tool_result 等资源。
- **任务一致性**：`TaskMismatchDetector` 对不可信来源下的高风险工具动作进行任务文本匹配和否定模式检查。

### 源码证据

`events/resources.py` 对 `read_file`、`write_file`、`send_email`、`call_api`、`code_exec`、`memory_write` 等工具生成 canonical resources。`detectors/tool.py` 中的 `ToolHijackDetector` 比较实际工具类别、类型、资源方向和操作是否符合 profile；`UnprofiledToolResourceDetector` 对未画像工具触达 outbound、persistent、execute、write、delete 等高风险资源时输出 `ask`。

### 答辩价值

这让报告可以强调“行为语义检测”：AgentGuard 不是只看危险词，而是判断工具调用是否符合工具身份、资源方向和用户任务。

需要明确的是，当前 `TaskMismatchDetector` 是基于工具别名、文本归一化和中英文否定模式的确定性检查，不是语义模型或 embedding 检测。

## C4：`allow` / `deny` / `ask` 三态审批闭环

### 问题

Agent 场景中很多操作并非绝对恶意。例如外发邮件、写入记忆、调用 API 在某些业务任务中是合理的，但在上下文不足或来源不可信时又可能存在风险。纯二态决策会在安全性和可用性之间产生冲突。

### 设计决策

AgentGuard 引入第三态 `ask`：

| 决策    | 适用场景               | 执行方式                               |
| ------- | ---------------------- | -------------------------------------- |
| `allow` | 未触发规则或风险可接受 | Adapter 继续执行                       |
| `deny`  | 明确高风险行为         | Adapter 阻断副作用                     |
| `ask`   | 中等风险或上下文不足   | Guard API 创建审批，Dashboard 人工确认 |

Core 只表达审批意图；审批状态、approval nonce、CSRF 校验、browser session 和 wait 流程由 Guard API / Control Plane 管理。Adapter 只能等待自己发起的审批结果，不能直接 resolve 审批。

### 源码证据

`services.py` 中 `ApprovalService.create_for_decision()` 仅在 `decision == "ask"` 且存在 `approval_intent` 时创建审批记录；`main.py` 中 `/v1/approvals/{approval_id}/resolve` 校验 browser session、CSRF token 和 approval nonce；`/v1/approvals/{approval_id}/wait` 校验等待方 principal。

### 答辩价值

三态设计能说明项目不仅追求“拦截率”，也考虑正常业务任务的可用性。高风险动作拒绝，低风险动作放行，边界动作进入人工确认。

## C5：审计 hash chain 与 provenance graph

### 问题

如果系统只能给出一次性阻断结果，却不能说明事件来源、命中规则、审批过程和证据链，那么答辩展示和事后复盘都会很弱。

### 设计决策

AgentGuard 在 Guard API 中维护两类证据：

- **审计完整性**：为审计事件附加 sequence、prev_hash、event_hash，并通过 `verify_audit_chain()` 校验顺序和哈希。
- **溯源图谱**：记录 event、decision、audit、action critic 等节点，以及 `evaluated_to`、`recorded_as`、`reviewed_by` 等边。

### 源码证据

`apps/guard-api/guard_api/storage/integrity.py` 实现 `attach_audit_integrity()`、`compute_audit_event_hash()` 和 `verify_audit_chain()`；`services.py` 中 `AuditService` 在记录评估结果时写入 provenance nodes/edges；`TraceService.get_provenance()` 提供 trace 级别的证据图查询。

### 答辩价值

这让系统能够回答评委关心的三个问题：为什么拦截、谁审批、证据是否连贯。需要注意，hash chain 提供的是本地审计篡改发现能力，不等同于外部可信账本。

## C6：面向副作用的 AttackBench 评测与跨运行时适配

### 问题

许多 LLM 安全评测只看最终文本，而 Agent 攻击真正重要的是副作用是否发生：文件是否被读、数据是否外发、记忆是否被污染、业务动作是否被完成。

### 设计决策

AttackBench 以 AttackCase 为核心组织样本、runner、scoring 和 metrics。当前 `AttackType` 覆盖：

- `prompt_injection`
- `tool_hijacking`
- `memory_poisoning`
- `file_exfiltration`
- `agent_abuse`
- `benign`

主 AttackCase 数据集 123 条，PoisonedRAG 扩展 12 条，合计 135 条。`calculate_metrics()` 输出 `asr_before`、`asr_after`、`asr_valid`、`block_rate`、`fpr`、`benign_fpr`、`task_success_rate`、`invalid_run_rate`、`metrics_reliable` 等指标。未重新运行得到的数值不写入结论，只保留为待实测项。

### 源码证据

`agentguard_langgraph_bench/bench/models.py` 定义 AttackCase 和 AttackType；`bench/metrics.py` 计算指标可信度和防御前后结果；`bench/datasets/attack_cases/` 和 `bench/datasets/poisonedrag/attack_cases/` 提供当前样本文件。

### 答辩价值

AttackBench 让 AgentGuard 的防御效果从“主观上看起来安全”变为“围绕副作用、误报和任务成功率可复查”。这也是项目相比普通文本过滤器更适合竞赛展示的地方。

## 与已有工作的关系

AgentGuard 与已有研究和标准之间的关系可以这样表述：

| 相关工作或标准                          | 对 AgentGuard 的启发                                                             | AgentGuard 的工程落点                                 |
| --------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------- |
| ReAct、Toolformer                       | 说明模型调用工具已成为重要范式                                                   | 将安全控制放到工具动作前后                            |
| AgentDojo、InjecAgent、间接提示注入研究 | 揭示工具型 Agent 面临间接注入和任务劫持风险                                      | 将风险转化为事件、规则命中、审批和审计                |
| OWASP LLM Top 10                        | 强调 prompt injection、sensitive information disclosure、excessive agency 等风险 | 对应上下文注入、敏感资源/外发检测和执行前控制         |
| MCP Specification                       | 工具生态标准化带来工具描述、权限边界和跨工具调用治理需求                         | 通过工具画像、资源派生和 adapter 层提供运行时控制入口 |

AgentGuard 的贡献不是替代上述工作，而是把相关风险认识落到一个可运行、可审计、可展示的工程系统中。

## 答辩亮点表达

以下表述可直接转化为 PPT 要点：

> AgentGuard 的核心不是让模型“更听话”，而是在 Agent 准备调用工具时增加独立的安全裁判。

> 我们关注的是 Agent 的外部副作用：文件有没有被读、数据有没有被发、记忆有没有被写、工具有没有被劫持。

> `allow` / `deny` / `ask` 三态机制让系统能够区分低风险、高风险和需要人工确认的边界行为。

> 每次判断都留下证据：事件、规则、风险分、审批、审计 hash chain 和 provenance graph。

> 评测不是只看最终回答，而是看攻击是否真的造成行为后果。

## 边界声明

为保持材料可信，创新性说明应坚持以下边界：

- 不宣称 AgentGuard 训练了新的基础模型或提出了新的深度学习结构。
- 不把确定性规则包装成机器学习检测算法。
- 不承诺覆盖所有提示注入、所有工具攻击或所有部署风险。
- 不把未重新运行的 ASR、FPR、延迟或准确率写成既定结果。
- 不把 OpenClaw hook-only 插件表述为接管所有 OpenClaw 安全能力。

更准确的结论是：AgentGuard 基于事件契约、确定性规则、工具画像、资源派生、三态审批、审计溯源和副作用评测，构建了一套面向工具增强型 Agent 的运行时行为安全监督原型。它的优势是工程链路完整、证据表达清晰、答辩展示友好；后续仍需要更大规模数据集、多语言场景和真实业务部署验证。
