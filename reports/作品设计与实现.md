# 作品设计与实现

## 2.1 设计目标

AgentGuard 的设计目标是在不改动模型参数、不重写业务工具的前提下，为工具增强型 Agent 增加运行时安全控制。系统需要满足以下要求：

- 执行前拦截：高风险工具调用、消息发送和记忆写入应在副作用发生前被评估。
- 框架解耦：安全判定逻辑不绑定 LangGraph、OpenClaw 或某个具体工具运行时。
- 可解释判定：每次判定需要输出规则命中、风险分、严重等级和原因。
- 状态隔离：Core 保持无状态；策略、审批、审计和指标由 Control Plane 管理。
- 可评测：攻击样本、良性样本和防御前后结果能够被 AttackBench 复现和汇总。

## 2.2 四层架构实现

### Runtime Adapter

Adapter 层负责把不同 Agent runtime 中的原始事件映射为标准 `GuardEvent`，并把 `GuardDecision` 映射回运行时动作。

LangGraph 侧的重点实现是 `SecureToolNode` 与 `GuardedToolGateway`。`SecureToolNode` 包装工具节点并维护 `behavior_events`；`GuardedToolGateway` 在调用真实工具前执行 `evaluate_before_tool()`，若决策为 `deny` 或 `ask`，则返回 blocked result，真实工具不会执行；若决策为 `allow`，才调用工具并记录 side effects diff。

OpenClaw 侧实现为 `@agentguard/openclaw-plugin` hook-only 插件。当前注册 16 个 hook，其中 `before_tool_call`、`message_sending`、`before_install` 是阻断面，`tool_result_persist` 是工具结果观察面，另外 12 个 gateway/session/model/subagent/cron/exec-env hook 用于运行时观察审计。插件通过 adapter token 调用 Guard API，并对工具调用、消息发送和安装配置审计采用 fail-closed 策略。

### Guard API / Control Plane

Guard API 是系统唯一对外控制面，基于 FastAPI 实现。它承担以下职责：

- `/v1/guard/evaluate`：接收 `GuardEvent`，鉴权后调用 Core，返回 `GuardEvaluationResponse`。
- 策略管理：提供 current/history/validate/diff/rollback 等接口，维护 `PolicyBundle` 当前快照和历史版本。
- 审批流：对 `ask` 决策创建审批记录，Dashboard 通过 session + CSRF resolve，Adapter 通过 bearer token wait。
- 审计与溯源：写入审计事件，维护 hash chain，并记录 provenance nodes/edges。
- 评测与指标：保存和查询 evaluation run，暴露 eval metrics。
- Adapter 状态：接收 OpenClaw heartbeat，记录 hook 数量、运行时版本和 fail-closed 能力。

### agentguard-core

Core 是无状态 Python 判定库。其稳定接口为：

```python
def evaluate(event: GuardEvent, policies: PolicyBundle | None = None) -> GuardDecision:
    ...
```

`GuardEngine` 每次调用只依赖当前 `GuardEvent` 和传入的 `PolicyBundle`。默认检测器列表按顺序执行，所有 `DetectionResult` 由 `build_guard_decision()` 合并。若没有规则触发，输出 `allow`；若任一检测结果为 `deny`，整体输出 `deny`；否则若任一检测结果为 `ask`，整体输出 `ask`；风险分取触发结果中的最高值。

### Dashboard / Evaluation

Dashboard 当前包含 overview、approvals、investigations、evidence、evaluation、system 等页面，展示决策趋势、攻击分布、规则 Top N、审批队列、证据详情、provenance graph、评测指标和系统状态。Evaluation 侧通过 AttackBench 组织样本、执行 runner、计算 ASR、Block Rate、FPR、Task Success Rate 和运行质量指标。

## 2.3 GuardEvent 事件契约

Core 定义 7 类 `GuardEventType`：

| 事件类型                | 说明                                        |
| ----------------------- | ------------------------------------------- |
| `tool_call_proposed`    | Agent 拟调用工具，通常在工具执行前触发      |
| `context_assembled`     | 上下文或 RAG 来源已组装，准备进入模型上下文 |
| `model_input_prepared`  | 模型输入准备完成                            |
| `model_output_produced` | 模型输出生成完成                            |
| `tool_result_produced`  | 工具结果生成，可能进入上下文或持久化        |
| `memory_write_proposed` | Agent 拟写入长期记忆                        |
| `message_send_proposed` | Agent 拟发送消息或外发内容                  |

`_EVENT_PAYLOAD_CONTRACT` 将每类事件绑定到对应 payload 模型。除 `tool_call_proposed` 外，`context_assembled`、`model_input_prepared`、`model_output_produced`、`tool_result_produced`、`memory_write_proposed`、`message_send_proposed` 还定义了 raw payload 必需字段校验。`tool_call_proposed` 使用 `ToolCallPayload` 的结构化字段表达工具名、参数、工具元信息和派生资源。

这种事件契约的作用是把不同 runtime 的原始事件转换为统一安全语义，使检测器不需要了解 LangGraph、OpenClaw 或其他框架的内部对象。

## 2.4 资源派生与工具画像

AgentGuard 不只检查文本，还从事件中派生资源、操作和数据方向。`derive_resources()` 会根据 payload 类型生成 canonical resources，例如：

- `read_file` / `write_file` 映射为本地文件 read/write。
- `send_email` 和 `message_send_proposed` 映射为 outbound message send。
- `call_api` 映射为 outbound API 请求。
- `code_exec` 映射为本地 process execute。
- `memory_write_proposed` 映射为 persistent memory write。
- `tool_result_produced` 映射为 inbound tool result context/persist。

`PolicyBundle` 中的 `ToolProfile` 定义默认工具画像，包括 categories、kinds、operations、directions。`ToolHijackDetector` 会对工具类别、类型、资源方向和操作类型进行一致性检查；`UnprofiledToolResourceDetector` 会对未画像工具访问 outbound、persistent、execute、write、delete 等高风险资源时输出 `ask`。

## 2.5 检测器与规则

当前 `GuardEngine` 默认组合 10 类检测器，对应 11 个主要规则入口：

| 检测器                           | Rule ID                                | 默认决策       | 主要依据                                                          |
| -------------------------------- | -------------------------------------- | -------------- | ----------------------------------------------------------------- |
| `SensitiveResourceDetector`      | `P001_sensitive_file_access`           | `deny`         | 派生资源目标包含 `.env`、token、secret、private key 等敏感标记    |
| `ToolHijackDetector`             | `P002_tool_identity_mismatch`          | `deny`         | 工具类别、类型、资源方向或操作与工具画像冲突                      |
| `TaskMismatchDetector`           | `P004_task_mismatch`                   | `ask`          | 不可信来源下，高风险工具动作与用户任务文本不清晰匹配              |
| `OutboundDetector`               | `P005_external_send`                   | `ask` / `deny` | 邮件或消息外发到非允许域名；包含敏感内容时拒绝                    |
| `OutboundDetector`               | `P006_outbound_api_review`             | `ask`          | API 请求指向 collection/upload/exfil/webhook 等收集端点           |
| `UnprofiledToolResourceDetector` | `P007_unprofiled_tool_resource_review` | `ask`          | 未画像工具访问高风险资源                                          |
| `PromptInjectionDetector`        | `P101_prompt_injection`                | `ask`          | 未净化的不可信 instruction-like 内容进入上下文或模型输入          |
| `JailbreakDetector`              | `P102_jailbreak`                       | `deny`         | 模型输入含越狱标记，或模型输出疑似泄露隐藏上下文/密钥             |
| `CodeExecDetector`               | `P103_code_execution_abuse`            | `deny`         | `code_exec` 命令含下载执行、删除、环境探测、外连等危险 shell 行为 |
| `MemoryPoisoningDetector`        | `P104_memory_poisoning`                | `ask`          | 不可信或需审批的长期记忆写入将持久化                              |
| `EnvironmentPoisoningDetector`   | `P105_environment_poisoning`           | `ask`          | 未净化工具结果含 instruction-like 内容且会进入上下文或持久化      |

其中 `TaskMismatchDetector` 的实现需要谨慎表述：它不是语义理解模型，也不使用 embedding 或外部 LLM，而是基于工具动作别名、任务文本归一化和中英文否定模式进行确定性匹配。因此它适合作为低依赖、可解释的启发式检测，但对语义等价改写和复杂上下文存在漏判风险。

## 2.6 三态决策与人工审批

AgentGuard 的决策不是简单二分类，而是 `allow`、`deny`、`ask` 三态：

| 决策    | 含义                   | 执行动作                                   |
| ------- | ---------------------- | ------------------------------------------ |
| `allow` | 未触发规则或风险可接受 | Adapter 放行工具或消息                     |
| `deny`  | 高风险或明确违规       | Adapter 阻断副作用并返回安全提示           |
| `ask`   | 中等风险或上下文不足   | Guard API 创建审批记录，Dashboard 人工处理 |

Core 只表达审批意图，不创建审批记录。Guard API 在收到 `ask` 后创建 `ApprovalRequest`，Dashboard 获取待审批列表时签发一次性 approval nonce；resolve 时校验 browser session、CSRF token、approval nonce、subject id 和可选决策。Adapter 只能等待自己发起的 approval，不能直接 resolve。

这种设计把“不确定但可能合理”的行为从自动拒绝中分离出来，降低误拦截对正常任务的影响，同时仍能在副作用发生前引入人工确认。

## 2.7 审计完整性与证据链

Guard API 对每次评估结果构造 `AuditEvent`，并记录：

- 原始事件、决策 id、approval id、critic review id 等链接。
- event、decision、audit、action critic 等 provenance 节点。
- `evaluated_to`、`recorded_as`、`reviewed_by` 等 provenance 边。
- 审计 hash chain 元数据，包括 sequence、prev_hash、event_hash 和 canonicalization。

`verify_audit_chain()` 会按顺序校验 sequence、prev_hash 和重新计算的 SHA-256 event hash。如果中间审计事件被篡改或缺失，完整性状态会指出首个 broken audit id。这一机制不等同于外部可信账本，但为本地审计记录提供了篡改发现能力。

## 2.8 AttackBench 评测框架

AttackBench 位于 `agentguard_langgraph_bench/`，包含样本、runner、scoring、metrics 和多种 runtime adapter。`AttackType` 当前覆盖 `agent_abuse`、`file_exfiltration`、`memory_poisoning`、`prompt_injection`、`tool_hijacking` 和 `benign`。

当前数据集规模可从 JSONL 文件确认：

| 数据集               | 用例数 |
| -------------------- | -----: |
| 主 AttackCase 数据集 |    123 |
| PoisonedRAG 扩展     |     12 |
| 合计                 |    135 |

指标计算函数 `calculate_metrics()` 区分 malicious、benign、valid/evaluable、blocked、task success、high confidence success 和 run quality，并输出 `asr_before`、`asr_after`、`asr_valid`、`block_rate`、`fpr`、`benign_fpr`、`task_success_rate`、`invalid_run_rate`、`metrics_reliable` 等字段。由于本次报告整理未重新执行 runner，具体数值需由最终评测命令生成后填入。
